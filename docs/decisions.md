# Decisions log

Dated, one-line entries for project-level decisions. Rule and wording decisions live in `decisions-v1.md`.

- 2026-10-07: Moved from cloud to local via git bundle; repo pushed to GitHub (private).
- 2026-10-07: Owner decisions for the call-to-booking router. Match window: booking `createdAt` from call start minus 2 min (clock skew) to call end plus 10 min (Cal.com webhook delay). Match order: phone hash, then attendee email, then the only candidate in the window. Phones are normalised to E.164 before hashing on both sides. The only-candidate match must not conflict with a different phone or email on the booking. Matching is triggered from both sides (post-call processing finishing; a Cal.com booking arriving) plus the tick; claiming is atomic, so the first to run wins. A sweep at call end plus 15 min raises the flags. All flags go to the design lead, never Nikhil (he only gets complaints, VIP referrers and high-value calls): ambiguous (2+) = design lead links by hand; agent claimed a booking but none matched = URGENT to the design lead plus a front-desk callback item; booking with no matching call = design lead, low priority.
- 2026-10-07: Router details I chose inside those decisions (owner to confirm or change): (1) the only-candidate step also requires that the agent said it booked, so a call that booked nothing can never take someone else's booking by elimination; a phone or email match does not need the claim. (2) An ambiguous result is flagged at the sweep, not at once, because a rival call may still claim one of the candidates. (3) Ambiguous is NORMAL priority (only "claimed but none matched" is URGENT, as specified). (4) A Cal.com booking is reported as having no call 45 min after Cal.com created it. (5) Extra design-lead alerts for cases the owner did not list: a booking matched to a call whose enquiry is not a "fit" (never booked, hard rule 2), a matched booking with no free eligible designer (URGENT), and a matched call with no saved enquiry. (6) A call with no booking claimed and none found just closes (not_fit stays not_fit); a fit enquiry still gets its HubSpot deal for follow-up. (7) Five failed routing attempts mark the item failed and alert the project owner (system failure, not Nikhil).
- 2026-10-07: Fixed a double-booking race in `recordExternalBooking`: a second simultaneous attempt for the same Cal.com booking used to fall through to the next designer; it now returns the booking the first attempt made.
- 2026-10-07: `design_lead_alert` outbox items were being queued (cancellations, complaint callbacks) but nothing delivered them. `AlertDrainer` now sends them to the design lead's Telegram chat; they wait if no design lead has a chat id.
- 2026-10-07: Owner confirmed router choices 1, 2, 4 and 5. Choice 3 changed: an ambiguous match stays NORMAL priority but becomes URGENT when the earliest candidate consultation starts within 24 hours (exactly 24 h counts).
- 2026-10-07: Vaani -> pipeline wiring (prompt_only). The vaanivoice.ai webhook is `POST /api/vaanivoice/webhook/<VAANIVOICE_WEBHOOK_SECRET>` (Vaani documents no signature, so the secret is a path segment; a wrong segment is a 404). Only `call_postprocessing` is processed. Only the call id is read from the body: transcript, entities, caller number and times are re-fetched from Vaani's own API with our key, so a forged POST can at most trigger a lookup. Outbound calls are ignored (hard rule 5). A failed or not-ready fetch answers 503 (so Vaani may retry; whether it does is undocumented) and alerts the project owner once per call. `makeDeps` runs the pipeline in `prompt_only` mode by default (`pipelineMode: "live_tools"` is kept for the tool-driven tests and simulator). The old vaanilabs.in mapper, its signature check and the `VAANI_*` env vars were removed.

(1) `crm_links.deal_amount_inr` added: the designers' deal value, only ever synced FROM HubSpot, shown only on the authenticated dashboard, never in a prompt, tool response, log, Telegram or email (a test greps `src/` for it). The "no price fields" migration test now allows exactly that column. (2) Funnel stages 8-10 (consultation held, quote sent, won) have no live source yet (nothing sets `bookings.status = attended` or a `crm_links.stage` past `new`): on live data they show "no data yet", not 0. The dashboard defaults to Live; Demo is a switch with a banner. `seed:demo:reset` deletes WHERE is_demo and refuses while real calls exist unless `--force`. Rows the dashboard itself writes about demo calls (review draw, phone reveal) inherit the call's flag. (4) Time to answer is computed literally from rang_at to answered_at; "median hand-off to designer accept" is sent_at to accepted_at, in working minutes (Mon-Fri 10-19), wall-clock shown beneath. (5) Weekly review: 10 random processed calls per IST week, drawn once and kept; "Agent was right" / "Overturn"; a reason is required to overturn a booked / escalated / not-fit decision; the reviewer name is self-declared (one shared dashboard token = no identity). Overturn rate = overturned / reviewed. (6) Phone reveal: POST only, logged in `phone_reveals` BEFORE the number is returned, 30 an hour, hidden again after 30 s; everywhere else only `callers.phone_masked` is ever selected. Per-person attribution needs real dashboard_users auth (open).

- 2026-10-08: Dashboard access (owner decision). Outside production (NODE_ENV is not "production") the dashboard and `/api/dashboard/*` need no token and show no login. In production there is one password screen (`DASHBOARD_PASSWORD`, 12+ characters) and it fails closed: no password set means nothing opens (503 / "locked" screen). The decision uses NODE_ENV and the password only, never the Host header, the URL or any other request detail (a test sends faked Host and X-Forwarded-Host headers). The session cookie holds an HMAC derived from the password, not the password, and the password is accepted as a bearer token for API use but never from the URL. Because there is no named login, phone reveals are logged as `who = 'local user'` locally and `'dashboard'` behind the password, and weekly-check overturns are recorded as "local user" locally (behind the password the reviewer types a name, self-declared). `DASHBOARD_TOKEN` and the token login were removed.
